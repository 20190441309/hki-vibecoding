## 什么是 Vibe Coding？

**Vibe Coding** 是由 OpenAI 联合创始人 **Andrej Karpathy** 于 2025 年 2 月提出的 AI 辅助编程范式。核心是：**用自然语言描述需求，AI 生成代码，通过对话迭代优化**——不再需要逐行手写。

可以归结为三个字：**见（See）→ 说（Say）→ 跑（Run）**

这不仅是"让 AI 帮忙写代码"——你从**编码者**变成了**需求描述者和质量审核者**。

### 适合什么？

✅ 快速验证创意的 MVP、个人项目、前端页面和小工具、学习编程  
❌ 不适合：金融/医疗等高安全性系统、多人大型代码库（缺乏规范时）、安全敏感核心逻辑

### Vibe Coding vs 传统编程

| 维度 | Vibe Coding | 传统编程 |
| ------ | ------------ | --------- |
| 上手门槛 | 极低，非程序员可用 | 需系统学习 |
| 原型速度 | 极快（数小时出 MVP） | 慢但稳定 |
| 可维护性 | 较差，易积累技术债 | 强 |
| 安全风险 | 漏洞概率约高 2.74 倍 | 相对可控 |

> 🧪 一个反直觉的研究：有经验的开发者在使用 AI 编程后，实际效率**慢了 19%**，因为花大量时间审查和修复 AI 生成的代码。

## 避坑指南 & 效率技巧

### 什么时候不该用 AI

1. **理解已有代码时** - 先自己读代码理解逻辑，再让 AI 帮忙修改
2. **安全敏感代码** - 永远不要盲目信任 AI 生成的认证、加密逻辑
3. **微小改动** - 改个变量名这种，自己改更快

### 提示词技巧

- **给上下文**：不要说"帮我写个函数"，而是"在 React 项目中，我需要一个处理用户登录的函数..."
- **指定输出格式**：告诉 AI 你要什么格式（代码、列表、表格）
- **分步骤要求**：复杂任务拆成多轮对话，每轮聚焦一个子问题
- **用 @ 引用文件**：不要描述路径，直接 `@src/auth/session.ts`
- **提供验证标准**：写测试用例、截图对比、明确期望输出

### Prompt 万能公式

```
[做什么功能] + [具体文件] + [技术要求] + [样式要求] + [验证标准]
```

## 18 条实战血泪经验（来自 2500+ 次 AI 对话）

### 准备阶段

**1. 把想法写清楚** — 回答三个问题：解决什么问题？用户怎么用？最重要的三个功能？

**2. 先画界面** — 用 v0.dev 或 21st.dev 先决定布局和区块，再让 AI 编码。

**3. 学会用 Git** — AI 随时可能搞烂代码。新手只需要三行命令：

```bash
git add .
git commit -m "完成了登录功能"
git push
```

> 每完成一个"能跑"的功能就 commit 一次。

**4. 选主流技术栈** — AI 靠网络教程训练，用的人越多它越会写。

| 用途 | 推荐 | 原因 |
| ------ | ------ | ------ |
| 前端 | Next.js | AI 最懂 |
| 数据库 | Supabase | 免费、免运维 |
| 样式 | Tailwind CSS | 写起来最快 |
| 部署 | Vercel | 一键上线 |

### 编码阶段

**5. 设定 Cursor Rules** — 告诉 AI 你的技术栈、编码规范、什么不能动。

**6. 建参考文件夹** — 放组件示例、API 模式、样式规范，AI 看到例子比描述理解得好 10 倍。

**7. 拆解复杂功能** — AI 一次做太多会"发疯"。按层构建：数据模型 → API → UI，每层验证后再继续。

**8. 管理对话长度** — 超过 30 轮或 AI 开始忘记规则，就 `/clear` 开新会话。

**9. 防止 AI 擅自做主** — 每次 prompt 末尾加这句：

```
重要：请「只」做我明确要求的事，不要修改或优化其他代码。
```

**10. 建立"AI 常犯错误清单"** — 创建 `ai-mistakes.md`，记录 AI 反复犯的错，新功能前引用它。

### 品质管控

**11. 代码审查 5 点清单（必做）：**

1. **Security inputs** — 用户输入有验证吗？SQL 参数化了吗？
2. **Error handling** — 代码处理了失败情况吗？
3. **Hardcoded values** — API 密钥、密码写在源码里了吗？
4. **Dead code** — 有未使用的函数和 import 吗？
5. **Logic coherence** — 函数实际做的和注释一致吗？

**12. 7 个安全重点：**

| # | 规则 | 说明 |
| --- | ------ | ------ |
| 1 | 不信任用户输入 | 参数化查询，不拼接 SQL |
| 2 | API 密钥不放前端 | 用环境变量，加 .gitignore |
| 3 | 检查权限，不只检查登录 | 登录 ≠ 有权访问 |
| 4 | 错误信息别太详细 | 用户看友好提示，详情写日志 |
| 5 | 检查数据拥有权 | 防止 IDOR 攻击 |
| 6 | 用数据库级安全 | 如 Supabase RLS |
| 7 | API 加频率限制 | 防止滥用 |

## 初学者常见 5 大坑

| 坑 | 现象 | 解法 |
| ---- | ------ | ------ |
| 🕳️ **厨房水槽式会话** | 一个会话做多个不相关功能，上下文全是噪音 | 不同任务间 `clear` 重置 |
| 🕳️ **反复纠正越改越错** | AI 做错了，纠正 5 次还是错 | 纠错超过 2 次就重开 |
| 🕳️ **CLAUDE.md 写太长** | 规则太多 AI 只执行前一半 | 保持 50 行以内 |
| 🕳️ **Vibe Coding 宿醉** | 初期飞快，几周后代码结构混乱 | 一开始就建立规范和测试 |
| 🕳️ **信任而不验证** | AI 生成看起来对的代码，但没有边界处理 | 永远提供验证标准 |

## 常见误区

| 误区 | 真相 |
| ------ | ------ |
| "有 AI 就不用学编程" | 仍需要懂基本逻辑、能读代码、会调试 |
| "Vibe Coding 就是偷懒" | 这是将认知从实现转移到需求定义和质量验证 |
| "AI 写的代码直接能用" | 必须审查！AI 输出约 80% 正确 |
| "只有高手才能用" | 初学者受益最大，但需要正确方法 |
